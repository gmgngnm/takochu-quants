# takochu-quants

国内プライム株を対象とした、**週次スイング（保有期間1週間程度）** のファンダメンタルズ分析基盤。

現在の到達点は **フェーズ1: データ基盤 + バックテスト基盤**。
売買提案までは出るが、**発注機能は意図的に入れていない**（理由は後述）。

---

## 設計上の前提

着手前に確認しておくべき、この構想の制約を明記しておく。

### 1. 「四季報を自動で読む」はできない

会社四季報の誌面データ（特に東洋経済独自の業績予想と記者コメント）は
法人向け有償提供のみで、四季報オンラインを契約してもスクリーニング結果を
一括エクスポートすることはできない。スクレイピングは利用規約違反。

そこで本プロジェクトは、**四季報の情報源である一次情報を直接取りに行く**。

| 四季報の誌面ブロック | 本プロジェクトでの取得元 | 状態 |
|---|---|---|
| 業績実績・財務 | J-Quants `/fins/statements`（決算短信XBRL由来） | 実装済み |
| 会社予想 | 同上 `Forecast*` | 実装済み |
| **業績予想の修正** | 同上を開示順に差分 | 実装済み |
| 配当・株式数 | 同上 | 実装済み |
| 株価・PER・PBR・信用残 | J-Quants 各エンドポイント | 実装済み |
| 業種・市場区分 | J-Quants `/listed/info` | 実装済み |
| 【特色】【連結事業】CF・大株主 | EDINET XBRL | フェーズ3 |
| **【業績記事】記者コメント** | **Claude で機能代替** | 実装済み（本文の取得経路は要整備） |
| **東洋経済独自予想** | 『会社四季報CD-ROM』を年4回・手動でCSV取込 | フェーズ4 |

取得できないのは実質「独自予想」と「記者コメント」の2つだけで、
記者コメントはむしろ Claude の得意領域（開示文からの定性抽出）に置き換えられる。

### 2. 「静的バリュエーション × 1週間保有」は時間軸が合わない

PER や ROE の水準が価格に反映されるのは数ヶ月〜数年スケール。
1週間の値動きを支配するのは需給とニュースで、バリュエーションの絶対値はほぼ効かない。

一方で、**ファンダ由来で1週間スケールに効く現象は実在する**:

- **PEAD（決算発表後のドリフト）** — サプライズの大きい決算後、株価が数日〜数週間同方向に漂う
- **業績予想の上方/下方修正** — 開示直後の数日間

したがって本プロジェクトは、バリュエーションの「水準」ではなく
業績見通しの「**変化**」を主軸に据えている（スコア重みも revision が最大）。

### 3. 日経新聞の記事は使えない

日経の利用規約は、自動取得（スクレイピング）だけでなく
**情報解析・機械学習目的での利用そのもの**を禁止している。購読していても同じ。
したがってシステムには組み込まない。

代替は一次情報（TDnet 適時開示・EDINET・企業IR）。日経記事の大半はこれらの後追いで、
独自価値のあるスクープは朝刊時点で寄り付きに織り込まれており、自動売買では取れない。

**日経の正しい使い方は、人間が読んで週次提案をレビューする段階で使うこと。**
これは規約上まったく問題なく、かつ機械には真似できない付加価値になる。

## 使い方

```bash
pip install -e ".[dev]"
cp .env.example .env    # J-Quants の認証情報を記入

takochu ingest --start 2018-01-01   # データ取り込み（再実行で差分のみ）
takochu features                    # 特徴量パネルを構築
takochu doctor                      # データ健全性を点検
takochu backtest --out reports/     # 週次リバランスを検証
takochu screen                      # 最新断面の候補銘柄を端末に表示
takochu monitor --stop-loss 0.05 --take-profit 0.08   # 保有中の手仕舞い点検

# 定性層（要 ANTHROPIC_API_KEY、pip install -e ".[llm]"）
takochu analyze --dry-run           # 呼び出し件数だけ確認
takochu analyze --detail-top 100    # 決算開示を Claude で定性分析
takochu features                    # 分析結果をパネルに反映

# 週次レポート（案Aの成果物）
takochu report --capital 10000000
takochu pwa --capital 10000000    # iPhone のホーム画面に置ける PWA
```

### 毎週の運用

```
金曜 引け後  takochu ingest && takochu analyze && takochu features && takochu report
月曜 朝      レポートを 10 分レビュー → 証券会社のアプリで手動発注
```

## アーキテクチャ

```
J-Quants API
    │  ingest/     生データをそのまま Parquet に（加工しない）
    ▼
data/raw/          daily_quotes, statements, listed_info, announcement, ...
    │  universe.py   プライム × 流動性 × 規模 を日次で判定
    │  features/     価格特徴量 + PIT なファンダ facts
    ▼
data/derived/panel.parquet    (Date, Code) の特徴量パネル
    │  strategy/score.py   断面 z-score → 合成スコア → ポートフォリオ
    ▼
backtest/        週次リバランスをコスト込みでシミュレート
    │
    └→ screen     最新断面の売買提案（発注はしない）
```

### Point-in-Time が最重要

`src/takochu/pit.py` がこのプロジェクトの心臓部。

決算は「決算期末日」ではなく「**開示された瞬間**」から使えるようになる。
これを取り違えると未来の情報で過去を判断する look-ahead bias が入り、
**バックテストだけが綺麗に勝つシステム**が出来上がる。

規約:

- `available_date` = その情報で引け値ベースの判断ができる最初の営業日
- 引け後（15:00 以降）の開示は**翌営業日**から使える
- 開示時刻が欠損している行は、安全側（引け後）に倒す
- パネルへの結合は DuckDB の `ASOF JOIN` で行い、構造的に未来を参照できなくする

### Claude 定性層（フェーズ2）

四季報の【業績記事】に相当する定性評価を、決算開示から生成する層。
記者の取材部分は再現できないが、公開情報の要約・評価は自動化でき、しかも
年 4 回更新の四季報と違って**開示のたびに更新される**ぶん鮮度で上回る。

設計上の制約を 3 つコードに焼き込んである:

1. **システムプロンプトは凍結** — 日付や銘柄名を一切入れない。prompt caching は
   前方一致なので、1 バイト変わると以降のキャッシュが全部無効になる
2. **株価を見せない** — 値動きを渡すと「上がっているから良い決算だ」という後知恵
   バイアスが入り、定量特徴量と相関するだけの冗長なスコアになる
3. **開示文書はデータであってプロンプトではない** — 文書内に指示文があっても
   従わないよう明示している（プロンプトインジェクション対策）

出力は JSON Schema で構造化を強制する。自由文で「買いです」と言わせない:

| 項目 | 内容 |
|---|---|
| `earnings_quality` | 利益の質（本業の実力か、一過性要因による嵩上げか）。+2〜-2 |
| `guidance_tone` | 見通し表現の強気・弱気。数値ではなく**表現**を見る。+2〜-2 |
| `catalysts` | 文書に書かれた具体的な材料（一般論は除く） |
| `risk_flags` | 閉じた enum。文書中に根拠があるもののみ |
| `confidence` | 確信度。**低い確信度は減点ではなく正直な申告として扱う** |

合成スコアは `(earnings_quality + guidance_tone) / 2 × confidence`。
確信度で減衰させることで、定型文だけの情報量が乏しい開示が断面順位を動かさない。

**コストは 2 段構え**で抑える: 全開示を Claude Haiku 4.5 でスクリーニングし、
定量スコア上位だけを Claude Opus 5 で精査する。結果は開示 1 件 ×
プロンプト版 × モデル でディスクにキャッシュするので、再実行では API を呼ばない。
Opus 5 では安全分類器による拒否に備えて `fallbacks="default"` を有効にしてある
（`--no-fallbacks` で無効化可能）。

> **未整備の部分**: J-Quants の `/fins/statements` が返すのは XBRL 由来の**数値**で、
> 決算短信の「定性的情報」**本文は含まれていない**。現状は
> `data/disclosures/<DisclosureNumber>.txt` に置かれたテキストを読む方式で、
> このファイルを用意する経路（EDINET 本文 / TDnet PDF からの抽出）はフェーズ3。
> テキストが無い開示は単に分析対象から外れるので、一部だけ揃った状態でも動く。

**LLM スコアも他のファンダ特徴量とまったく同じ PIT 規約に従う。**
開示の `available_date` で ASOF JOIN されるので、ここから未来の情報は漏れない。

### 週次レポート

`takochu report` が単一 HTML ファイル（外部リソースなし）を出す。
メール添付でもブラウザでもスマホでも読め、ダークモードにも追従する。

- 買い（保有目標）: ウェイト・**単元株に丸めた株数**・スコア内訳・主要ファンダ
- 売り（入替）: 前回保有から外れた銘柄
- 定性分析: Claude が抽出した根拠とリスクフラグ
- 目標ウェイトが 1 単元に届かない銘柄があれば警告する（小口資金では実際に起きる）

冒頭に「これは売買提案であって発注ではありません」のバナーを固定で出している。

### 使う証券会社

**このシステムは証券会社を選ばない。** 発注機能を持たず売買提案を出すだけなので、
いま使っている口座（SBI証券でも何でも）のまま使える。新しく口座を作る必要はない。

必要なのは証券口座ではなく **J-Quants の契約**（JPX のデータ配信サービス）で、
これは証券会社とは無関係に単独で契約する。

新しい口座が要るのはロードマップ7（自動発注）に進むときだけ。そのときは
HTTPS の JSON API を持つ立花証券e支店が第一候補になる。

### 保有と手仕舞い

`config/default.yaml` の `holding` で決める。

| 設定 | 意味 |
|---|---|
| `weekend_flat` | `true` で金曜の引けに全て手仕舞い、週末はノーポジ。月曜の寄りで入り直す |
| `take_profit` | エントリーからの変化率で利確。例 `0.08` = +8% |
| `stop_loss` | 同じく損切り。例 `0.05` = −5% |
| `stop_loss_atr` | ATR 倍率での損切り。固定率と併用した場合は**浅いほう**を採る |

利確・損切りは週の途中でも発動し、バックテストにも反映される。
日足しか無いので「その日の高値・安値がトリガー価格に届いたら、その価格で約定した」
とみなす。**同じ日に両方へ触れたら保守的に損切り側**を採り、
ギャップで飛び越えた場合はトリガー価格ではなく寄り値で約定したものとして計算する。

#### 週末ノーポジのコスト

ギャップリスクを避ける代わりに何を払うのかは、必ず数字で確認すること。
以下は合成データでの実測値（リターンの絶対値には意味がないが、**コストは実数**）。

| 設定 | 年率コスト | 平均回転率 |
|---|---|---|
| 持ち越し（既定） | 3.1% | 0.30 |
| 持ち越し + 損切5% 利確8% | 5.9% | 0.56 |
| **週末ノーポジ** | **17.6%** | **1.69** |

週末ノーポジは毎週全額を売って全額を買い直すので、回転率が 0.3 → 1.7 に跳ね上がり、
**コストが年 3.1% から 17.6% に増える**。金曜引けから月曜寄りのギャップが
年 17.6% 以上のマイナス期待値でない限り、これは割に合わない。
実データで両方を回して比較してから決めること。

### 保有中の監視

`takochu monitor` が、保有銘柄のうち利確・損切りの水準に達したものを洗い出す。
毎日引け後に回す想定。結果は `derived/alerts.json` に書かれ、PWA の先頭に
「手仕舞い（優先）」として表示される。

判定は**終値ではなく高値・安値**で見る。逆指値を置いていればザラ場で約定しているはずで、
終値だけ見ると見落とすため。

> **ザラ場でのリアルタイム判定はできない。**
> J-Quants は日足しか返さないので、到達を知るのは最短でも当日の引け後、
> 手仕舞えるのは翌営業日。板（気配値）も取得できない。
> ザラ場で即座に反応したいなら、証券会社の API（kabuステーション / 立花証券e支店）で
> **エントリーと同時に逆指値注文を証券会社側に置く**のが正解。
> そうすればプログラムが落ちていても損切りは機能する。

### iPhone アプリ（PWA）

`takochu pwa` が、ホーム画面に追加できる PWA 一式を書き出す。
用途は「読む」ではなく **確認して発注する** こと — 月曜の朝に1銘柄ずつタップで
確認し、最後に発注メモをコピーして証券会社のアプリに移る導線。

- 売り → 買いの順に並ぶ（先に手仕舞ってから買う）
- 各銘柄をタップで確認済みに。進捗は端末内に保存される
- **1単元に届かない銘柄は「見送り」と明示**し、発注メモからも外す
- Service Worker でオフラインでも開く。キャッシュ名は週ごとに変わるので
  古い週の内容が残らない
- データは `index.html` に埋め込む。別ファイルを fetch しないので、
  保有銘柄が余計にネットワークを流れない

```bash
takochu pwa --capital 10000000
python -m http.server 8000 --directory data/pwa    # 手元で確認
```

> ホーム画面に追加して「アプリらしく」動かすには **HTTPS が必要**。
> 静的ホストに置き、Safari で 共有 → ホーム画面に追加。

#### デモの配置（GitHub Pages）

`.github/workflows/deploy-pwa.yml` が UI デモを Pages に配置する。

**このリポジトリは public なので、ワークフローは合成データ（架空の銘柄）しか扱わない。**
実データを公開 Pages に載せる経路は意図的に作っていない。ビルド後に
`isDemo` の印がなければ公開を止めるガードも入れてある。

実データで使う場合は、`takochu pwa` の成果物を**プライベートなホスト**に置くこと:

| 方法 | 注意 |
|---|---|
| プライベートリポジトリ + GitHub Pages | プライベート Pages は GitHub Pro が必要 |
| Cloudflare Access / Netlify のパスワード保護 | アクセス制限を必ず掛ける |
| 自宅サーバー + Tailscale | 一番安全 |

保有銘柄・株数・資金額がそのまま載る。認証なしのホストには置かないこと。

### リーク検出テスト

`tests/test_backtest.py::test_無情報データではICが立たない` が最後の砦。

銘柄間に予測可能な差が**無い**データを流し、Information Coefficient が
0 付近に落ちることを検証する。ここで IC が立つなら、それは戦略の予測力ではなく
どこかに未来の情報が漏れている証拠。

```
ドリフト有り（予測可能な差を仕込んだデータ）: mean_ic = +0.054
ドリフト無し（完全に無情報なデータ）        : mean_ic = -0.006
```

## 特徴量

### ファンダ（変化を測る）

| 特徴量 | 意味 |
|---|---|
| `revision_op` | 同一決算期における会社予想（営業利益）の変化率。**最重要** |
| `revision_age_days` | 直近の修正からの経過日数。修正直後ほどドリフトが効く |
| `progress_gap` | 通期予想に対する進捗率 − 四半期ペース。PEAD の代理変数 |
| `op_yoy` / `sales_yoy` | 前年**同四半期**比（累計値どうしを比較） |
| `op_margin_delta` | 営業利益率の前年同期からの変化 |
| `roe` / `equity_ratio` | 収益性・財務健全性。質の低い銘柄を落とす |

### チャート（タイミングとリスク推定）

`mom_12_1`（直近1ヶ月を除く12ヶ月モメンタム）、`ma_gap_20/60`、`dist_52w_high`、
`atr_pct`、`vol_20`、`rsi_14`、`turnover_z`

チャートの役割は銘柄選定ではなく、**ファンダで選んだ銘柄が需給的に逆行していないかの確認**。

### ユニバース

プライム（市場区分 `0111`）× 20日平均売買代金 3億円以上 × 時価総額300億円以上 ×
上場90日以上。さらに**保有期間中に決算発表を跨ぐ銘柄はエントリ対象から除外**する
（1週間保有で決算を跨ぐのはコイン投げになる）。

## バックテストの前提

意図的に厳しくしてある。ここを甘くすると机上でだけ勝つ曲線が出る。

- **判断**: 週の最終営業日の引け後。使う特徴量はその時点で入手済みのものだけ
- **執行**: 翌営業日の寄り付き。判断日の引け値では約定できない
- **コスト**: 片道 20bps（手数料＋スプレッド＋スリッページ）。
  週次リバランスは年50回転するので、**コストだけで年15〜25%を失う**
- **回転率**: 前期の「目標ウェイト」ではなく「値動き後の実ウェイト」と比較する
  （ドリフトを無視するとコストを過小評価する）
- **生存バイアス**: 上場廃止銘柄もデータに残っている限りそのまま扱う
- **レバレッジ**: なし（`max_gross: 1.0`）

### 見るべき指標

損益曲線の見栄えより **Information Coefficient**（スコアと将来リターンの順位相関）。

`|mean_ic|` が 0.02 を下回るなら、そのスコアに予測力はほぼ無い。
IC が立たないのに損益が良い場合、それは少数銘柄の偶然か、
どこかに look-ahead が残っている。

## なぜ発注機能を入れていないか

週1回・10〜20銘柄の発注は、人間が手で10分やれば済む。
自動化しても**週9分半の削減にしかならず、分析精度は1ミリも上がらない**。

一方で自動発注は、執行・約定管理・状態同期・障害復旧・建玉照合という
かなりの複雑性と、設計を誤れば口座を毀損するリスクを持ち込む。

**まず戦略の期待値をバックテストで確認するのが先。**
ステップ4で期待値が出ないなら、発注を自動化する意味は無い。

なお発注層を後付けするのは容易で、ここまでの投資は無駄にならない。
その際のブローカーは **立花証券e支店API**（HTTPS の JSON API で Linux から直接叩ける）が
最適。kabuステーションAPI は Windows 常駐が必要で、1週間スイングにその
リアルタイム性能は要らない。

### パラメータを増やさないこと

スコア合成の重みはバックテストで決めるものだが、
**触るパラメータは5個以内に抑える**。増やすほど過剰最適化になり、
検証期間だけ綺麗に勝つ曲線が出来上がる。
